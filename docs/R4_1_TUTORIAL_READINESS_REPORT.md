## Confirmed root causes and implementation

| Finding | Fix |

Signed socket cookies/bearer sessions resolve current roles; HTTP ping applies equivalent ownership. Anonymous cryptographic session capabilities remain supported. |
| Individual grading persisted a result without notifying the teacher; polling and socket deltas could race | Publish result notifications after individual/progressive/final updates. The teacher reconciles one authenticated HTTP snapshot at a time; sockets trigger refresh. Failed polls preserve the last roster; unchanged logical rows avoid repeated MathJax work. |
| Submitted semantic work was not recorded until hosted checking returned; concurrent retries could downgrade a completed identical revision | Save pending answer identity before provider work; retain revision/digest locks and reuse completed identical-identity grades. Canonical persisted totals remain authoritative; final records reject late changes. |

| FIFO provider reservations let background work delay checking; SDK retries could bypass accounting | Bounded semantic queue/transport waits and three-interactive-start fairness before the oldest background waiter. ## Classroom privacy and authoritative state

Teacher HTTP snapshots and monitoring subscriptions require quiz-owner teacher/admin authorization. Public/student rooms never receive the class roster, other names, sessions, scores or progress. Student private whiteboard membership requires the same account/bearer boundary as grading. Draft quiz control subscriptions are restricted. Pause, terminate and private whiteboard controls remain.

The monitor does not clear students on WebSocket disconnect or poll failure. Saved pending/failed grades remain separate from completed grades. Client score/status claims cannot finalize attempts or replace earned points. Monotonic ping revisions protect current-question display; finalization and persisted grades win over late pings. Existing canonical scoring, proof/digest identities, attempt locks, snapshot contracts, ordering and durable final acknowledgment remain intact.

## Owned jobs and recovery boundaries

`ownedJobs.ts`, `jobRoutes.ts`, shared types and `owned-tasks.js` support generation, worksheet solving and worksheet finalization. Acceptance validates/reserves capacity, serializes the owner/task/idempotency identity and acknowledges metadata persistence before returning a secure job ID. Concurrent duplicate requests create one job/draft and consume one accepted work lease. The UI retains a secret-free input fingerprint and retry key after acknowledgment and across Back/refresh; changing inputs or explicit Start another creates a new intent. Repeating unchanged generation after Back returns the existing completed job rather than creating another quiz. Status lookup checks owner directly, including retained jobs older than the list's newest 50 entries.

Server-only `ai_jobs` stores owner, safe task label, status, timestamps, completed/total, result quiz ID, sanitized error and hashed idempotency identity. It stores no key, token, raw upload or source question payload. History is capped at 2000 accepted records/seven days; creation and listing clean expired history. Private quiz drafts retain bounded completed-batch checkpoints. Active partial drafts reject authoring mutations so a worker cannot overwrite teacher edits. Final output is always a draft on the modern path.

Browser navigation survives after accepted 202. On process restart, persisted metadata and acknowledged private drafts survive; incomplete work becomes Interrupted, with its saved draft link recovered by job identity. Completed quiz linkage repairs the status-acknowledgment crash window. Credentials are never reconstructed and work is never automatically repeated. Job deadline is twelve minutes; worksheet solving retains its stricter four-minute deadline. Keep one writable process.

Extraction remains upload-bound: 20 in-memory recoveries, 24 MiB aggregate result cache, 30-minute idle expiry, owner plus original file-byte fingerprint. Re-upload identical files to retry failed pages without more provider extraction for successful pages. Raw uploads are not retained. A restart or an abandoned pre-response extraction may require re-upload and may not return a recovery handle. The open review page retains its current extracted work; full extraction restart/navigation resumability is not claimed. RMX retains its specialized existing path.

Cross-file context is copied only from an explicit visible item declaration to a unique printed target, retaining original item text, source IDs and context provenance. Even a unique cross-file transfer requires teacher confirmation of source membership before publication; repeated/conflicting identities never receive a guessed association.

## Short manual tutorial acceptance checklist

1. Use a draft with exact and open-ended items; define explicit step criteria and preview its saved student appearance. Upload two adjoining source images, confirm shared context/crops and resolve source warnings before publishing.
2. Join with three to five synthetic students; answer simultaneously while the teacher starts one generation job. Verify checked points, pending/failed grading and current questions in Live.
3. Disconnect/refresh one student, then pause/resume. Confirm the same attempt and answer restore, without duplicate students or stale totals. Submit/retry once and confirm one final result.
4. Preview another quiz during generation, return and refresh; open the same completed private draft from the task area. Repeat navigation during worksheet solving.
5. Rehearse process restart in staging only: unfinished jobs must show Interrupted with saved drafts, presence/control state must be unknown until reconfirmed, and provider calls must not silently restart. Inspect admin/persistence health before a real tutorial.
